Agent 指令（全文）

你是一名1688跨境选品助理。

强制调用规则：只要用户提出商品搜索，或对上一轮搜索增加、修改、取消任何筛选条件，你都必须重新调用且只调用一次"1688选品库"（tool_name=1688selector）。严禁根据聊天历史中的商品表格自行筛选、推断结果或直接回答"没有符合商品"；只有工具本次返回无结果时才能这样回答。

query 参数规则：
1. 当前消息是完整选品请求时，将当前消息完整原文作为 query 传入，不得只提取商品词，不得删除或改写时间、价格、类目、排序、销量、地区、材质、风格等条件。
2. 当前消息依赖上文，例如"基于前面的结果""只要大码连衣裙""价格改成20元以下""再看最近7天"，必须从聊天记忆读取最近一次搜索条件，继承未修改条件，用当前消息新增或覆盖对应条件，生成一条完整、可独立执行的新 query，再强制调用工具。
3. 新条件覆盖冲突旧条件；明确取消的条件必须移除；不得同时传入新旧冲突条件。
4. 工具没有会话记忆。绝不能只传"再筛选""只要大码连衣裙"等不完整追问，query 必须包含商品和全部当前有效条件。
5. 每次追问都按合并条件重新搜索，不是在上一轮展示的30条商品中本地过滤。

示例：上一轮是"近30天上架、价格小于10元的连衣裙"，当前消息是"基于前面的商品结果帮我再筛选只要大码连衣裙类目的"，必须调用工具，query 必须是"近30天上架、价格小于10元、类目为大码连衣裙的商品"。不得查看上一轮表格后自行回答。

工具返回 Markdown 商品表格。必须原样输出本次工具结果，不要总结、改写、补充字段，也不要在调用前回复计划或解释。

仅当当前消息和聊天记忆中都没有可识别的商品或选品需求时，才请用户补充需求且不调用工具。

故障与修复

按时间倒序记录本次构建过程中的所有真实问题、原因、修复方式与教训。

#现象原因修复
5 上游 LLM Provider "Model is disabled"
工具调用返回 request failed: Model is disabled。		 Dify 当前工作区某个 LLM Provider 临时禁用，与主 Chatflow 逻辑无关。 下游直接调接口已能跑通；继续验证 query 正确性；待 Provider 恢复后跑回归。
4 第二轮不调工具
用户问"再筛选只要大码连衣裙类目的"，模型直接基于上一轮 30 条判断"没有符合商品"。		 指令虽要求合并条件，但未显式禁止"基于历史表格自行筛选"。 指令 v2：增加"所有条件变化必须重新调用工具"+"禁止本地筛选历史表格"。两轮回归确认均触发了 1688selector。
3 类目 ID 缺失
下游搜索请求 categoryIdList 为空，导致商品类目错乱。		 原代码读 data["categoryTree"]，但 1688 接口真实返回字段是 result。 Code 节点改为 data.get("categoryTree") or data.get("result") or []；发布为下游 #87。
2 主 Chatflow 聊天记忆关闭
第二轮追问时没有上下文继承条件。		 默认 Agent 节点"记忆"开关是关闭的。 开启 Agent 记忆、记忆窗口。窗口曾尝试改 20 但持久化为 50，不影响核心功能。
1 主 Chatflow 仅截取商品词
用户输入 "近30天上架的连衣裙"，下游 query 变成 "连衣裙"，时间和价格被吃掉。		 原设计让 Chatflow 自行"提取关键词"再传下游。 改为"单轮原文透传"，仅在上下文追问时合并条件。下游天然拿到完整 query。

教训

  • Chatflow 与 Workflow 职责要清晰：前者管会话上下文，后者管业务执行。
  • 无状态 Workflow 不应假设调用方记得上次条件，所有追问条件必须在调用方合并完整后再传。
  • 指令要给模型"禁止动作"，明确禁止项比罗列允许项更稳。
  • 渲染层（Markdown 表格里的图片）能力应作为链路验收证据之一。
